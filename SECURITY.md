# Security boundary

## Renderer

The kit treats model output, tool output and document text as data. The registry checks application contracts. The fill validator checks the component name and version, fields, types, limits, nested fills and slots. The element checks authorship against its bound actor and applies its component rules before it renders. The envelope and stream readers check part types, refuse invalid fills and limit retained stream data. The thread uses declared element tags. The narration check compares explicit claims and is subject to length and error limits. It cannot verify the facts in free text. [Registry](src/render/registry.js), [fill validator](src/render/validate.js), [base element](src/primitives/base.js), [envelope contract](docs/contracts/envelope.md), [thread](src/thread/index.js), [narration check](src/narration/check.js).

The DOM helper creates elements and text nodes. It permits a fixed list of attribute names. Components use fixed names for direct attribute writes and use event listeners for events. Part names and ID references come from fixed names, application options or local counters. Fill IDs serve as data or lookup keys. Layout values select fixed tokens. Read more uses checked numbers for its size. Icons have fixed paths. Charts use fixed SVG tags, finite coordinates and text labels. A fill cannot supply markup, scripts or CSS rules to the built-in renderer. Code for a registered application element can write to the DOM. The application owns that code. [DOM helper](src/render/dom.js), [layout primitives](src/primitives/index.js), [read more](src/primitives/read-more.js), [chart](src/components/chart.js), [mount](src/kit.js), [catalog contracts](catalog/README.md).

Citations and rich links check the URL again when a person presses the control. The kit sends a cancelable event before it opens the link with `noopener,noreferrer`. The check applies to the URL that the kit opens. It cannot verify the destination of a link redirect. If page policy permits mail links, the shared parser requires one mailbox after decoding and refuses queries and fragments. The renderer, rich text field and offline queue use the same mailbox check. [Citations](src/components/index.js), [rich links](src/components/rich-text.js), [mailbox check](src/render/rich-text-value.js).

Image loading starts with an empty list of allowed origins. When the application enables it, an image can load before a press. The kit checks the scheme, origin and credentials of the URL in the fill. It omits the referrer. The guide page sets a matching `img-src` Content Security Policy. The browser applies that policy to redirects. The component shows its failure state when the policy blocks the destination. [Image rules](src/components/image.md), [guide](docs/guides/assemble.md#enable-images).

## Action path

The application binds the tool in `mount` or in the thread binding callback. The action state checks and copies the binding. Bound arguments take precedence. Extra argument names must be editable in the binding. A bound confirmation must pass before the kit creates a request. Buttons and forms check the fill against the binding. These checks cover the values shown to the person, such as labels, descriptions, titles, editable fields and typed edits. The data grid checks the bound row and column rules. The upload checks the bound label and the name, type, size and count of files. It does not read the file contents. [Kit helpers](src/kit.js), [thread](src/thread/index.js), [action state](src/actions/action.js), [buttons and forms](src/components/index.js), [data grid](src/components/data-grid.js), [upload rules](src/components/upload.md).

A request starts pending. A valid receipt with `ok: true` can show `Done`. A valid receipt with `ok: false` shows `Not done` and the reason if present. A local failure can also show `Not done` with a reason that says why the send could not start. A missing, refused or invalid receipt leaves the outcome unknown. An action button or form offers Retry and Cancel when the try gets no receipt or reaches its time limit. Retry keeps the key and uses a new id. Cancel clears pending identifiers. It does not undo a request that reached the service. [Action and receipt rules](catalog/README.md#the-request-and-the-receipt), [action controls](src/components/index.js), [thread actions](src/thread/README.md#actions).

The action state, the upload and the queue use the same receipt check. It checks the boolean result, the optional text fields and each supplied id and key. The action state accepts a matching pending key or an id of one of its tries. The upload checks the id of the pending file. The queue checks identifiers against its transport try before it gives the result to the caller with the caller's request id. Receipt messages and references show as text. These checks match the receipt to the request. They do not authenticate the service or prove that it did the action. [Receipt check](src/offline/queue.js), [action state](src/actions/action.js), [upload control](src/components/upload.js).

The thread keeps the result of a completed action button when a refused snapshot replaces it. A valid fill at the same position in the same message keeps that result if the application binding matches. The button stays done and cannot send again. [Thread actions](src/thread/README.md#actions).

A grid pauses saved edits and prevents retries while its fill is refused. It can still accept a receipt for its pending request. A valid fill lets the grid send the saved changes that still agree with the fill and the binding. [Data grid actions](src/components/data-grid.md#action-and-receipt).

## Offline queue and data source

The queue checks and stores a new action before send. A new record has version 1, a principal and only the fields that the queue uses. Adoption checks the full shape and size and requires a matching principal. Records of version 1 can omit the version field if they pass the same checks. An invalid record or a record of an unknown version with a matching principal shows as unreadable. Its entry has a fixed label and a valid key or a local key. The queue never sends or retries the entry. Dismiss removes the stored record before the entry leaves the list. Records of other principals or with no usable principal stay hidden and untouched. The queue screens argument names for likely credentials. This check cannot find all secrets, including secrets in argument values. [Queue](src/offline/queue.js), [offline queue contract](docs/contracts/offline-queue.md).

Each queue sends its waiting actions in order, one try at a time. There is no single send order across pages. With Web Locks, a closed queue holds its owner lock until the final storage operation of an active try settles. A second page can take the record only after the lock releases. The next try keeps the key and uses a new id. At the time limit the queue aborts the signal. The transport and service determine whether the operation can stop. A try with no valid receipt stays pending. A cancel completes after storage removal. If removal fails, the action stays pending. The queue checks for closure just before it calls the application's send function. The application supplies the credentials and checks its session. [Queue](src/offline/queue.js), [offline queue contract](docs/contracts/offline-queue.md).

The worker installs only listed files from the same origin. It omits credentials and fails if a file redirects. The cache name includes scope and version. The worker uses a cached file only after a network failure on a listed GET. It does not store live network responses or send actions. Its file cache is shared by principals. The application must list only files that are public to all principals. [Worker](src/offline/worker.js), [worker contract](docs/contracts/offline-queue.md#the-service-worker).

The data-source helper checks and copies requests. It checks result keys and filters, gives no records on error and freezes successful results. The helper has no cache or principal field. The application owns access to the records and isolation of any cache that supplies them. [Data-source helper](src/offline/source.js), [data-source contract](docs/contracts/data-source.md).

## What the application must do

- Set the actor of each envelope from trusted application or transport context. Apply the same rule to history. The kit checks the actor's shape and compares a fill's authorship claim with the bound actor. Page code can set `actorFor` on the thread and give it to the history reader. The kit refuses a message if the hook throws, returns an invalid actor, or returns a type or id that differs from the envelope actor. The application owns the trusted context for this check. [Envelope reader](src/envelope/envelope.js), [envelope contract](docs/contracts/envelope.md).
- If you enable model-supplied images, set a matching `img-src` Content Security Policy or use an image service that checks redirects. [Image rules](src/components/image.md).
- Implement the idempotency key rule in the service. Check the queue principal against the active session in the send function before you send. Close the queue before you change the credentials that the send function uses. [Send function and principal rules](docs/contracts/offline-queue.md).
- Own sign-in, credentials, access control and isolation of the application's data caches. Use the service to authorize each action and check uploaded file contents. Keep credentials out of bound arguments, stored edits and principal IDs. [Offline queue contract](docs/contracts/offline-queue.md), [data-source contract](docs/contracts/data-source.md), [upload rules](src/components/upload.md).

## Reporting

Use neutral data when you report a problem. For a possible vulnerability, use GitHub private vulnerability reporting. Do not post sensitive payloads or exploit details in a public issue. No response time is promised.
