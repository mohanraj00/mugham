# Changelog

Each release has an entry. The newest entry is first.

## Unreleased

- A docs panel on each example page (#100). The panel is next to the live example, and below it on a narrow screen. It has one part for each component of the page, with the element name, the keys of the contract with their types, the states, the slots, the events, the actions, a sample fill, and links to the component doc and the guide. `examples/docs.js` reads the keys from the contract in the registry, so the panel agrees with the contract. `examples/docs.json` gives the events, the actions and the samples. The inputs, the forms, the table and the data grid have a "How to" part: bind an action, read a receipt, show an error. A test validates each sample fill, and a browser check opens each part on each page.
- One entry point for the examples (#99). `examples/index.html` lists each example in groups, with a name, one sentence and a link, and it filters the list by a word. `examples/examples.json` is the one list of the examples. Each example page has the same frame from `examples/frame.js`: a link back to the index, the group, and the previous and next example. The example files are now in a folder for each group: `cards/`, `forms/`, `tables/`, `evidence/`, `thread/`, `media/`, `apps/` and `guides/`. The README and the docs give the new paths, and an old path such as `examples/loans.html` does not work. The quickstart starts at the index page. A browser check opens the index, filters it and follows each link.
- A default page style (#98) in `src/styles/page.css`. It sets the page ground, the page width, the page header, the headings, the text, links, code, and the plain tables and controls of a page. It uses only the tokens, loads no font and makes no request. The tokens get `color.page`, `color.border-subtle`, `space.5`, `space.6`, `type.heading-1` to `type.heading-3`, `type.code` and `size.page`, each from the brand tokens. The edge of a card, a form, a message, a diff and a chart is now a lighter mix of `color.border`, and a card, a form and a message have a small shadow from the same token. The edge of each control keeps the full border color. No contract changes. Each example uses the default style. [Theme the kit](docs/guides/theme.md#the-default-page-style) tells how a page uses the default style or its own style.
- The short form of a contract, format 3 (#103). A contract states only what is special about its component. `catalog/schema/defaults.json` holds the defaults of the catalog: the version, the kind, AI content with a required authorship slot, the state `default`, the base tokens and the base accessibility block. A field is not required, its label comes from its key, and a text field can name a size (`short`, `line`, `title`, `summary` or `long`). A list of states or tokens extends the default list with the `+` mark. A resolver gives the full form, which is format 2, and the kit reads only the full form. Each catalog contract has the short form, and its full form is equal to its content before this change, key for key. A contract in the full form stays valid, `register` accepts the two forms, and the format of a fill stays `2`. [catalog/schema/README.md](catalog/schema/README.md#short-form-format-3) gives the rules and the upgrade steps.
- Cards can collapse and expand (#96). The optional keys `collapsible` and `collapsed` add a keyboard toggle and set the start state. A collapsed card shows its title, status and optional short summary. Pending actions and actions that wait for a receipt stay visible. Each state change sends `mu-collapse`, and the kit saves no collapse state outside the element. Card grids have optional Expand all and Collapse all controls. The loans example shows both controls. Contract tests and browser checks cover the keys, the events, focus and the pending rule. [Card rules](src/components/card.md) gives the keys and the properties.

## 0.3.0, 2026-11-18

Upgrade from 0.2: an application that uses 0.2.1 needs no code change. The changes are new components and new optional keys, and the contract format stays `2`. A form with `typed` names in its binding asks for the edit type and sends an `edits` list. A form with no `typed` names works as before.

- The README lists each catalog component and each example page of the main branch, and `docs/STATUS.md` records the v0.3 scope as complete and not released.
- A snapshot compare example (#13) in `examples/tables/snapshots.html`, on a fixture API, `examples/tables/snapshots-api.js`, with synthetic versioned records. The page lists the collections and the snapshots in `mu-table`, shows the compare result of two snapshots with `mu-diff` and lists the records that the change affects. The example only reads, and the fixture API is the source of each result. The kit has no knowledge panel. A versioned store builds its own dashboard from the example. `tests/browser/snapshots.js` runs the flow in `make check` and proves that the page sends no action.
- A review queue example (#10) in `examples/tables/review-queue.html`, on a fixture API, `examples/tables/review-queue-api.js`, with synthetic tasks. The page lists the open tasks in `mu-table` and shows the source excerpt next to the extracted value. A reviewer accepts, rejects or corrects the value. A correction uses the typed edits of the form, and `mu-diff` shows the old value and the new value. The fixture API decides and gives the receipt, and the page shows `Done` only after it. The kit has no review panel. A service builds its own dashboard from the example. `tests/browser/review-queue.js` runs the flow in `make check`.
- The data grid component `mu-data-grid` (#73), with the contracts `data-grid`, `data-grid-column`, `data-grid-row`, `text-cell`, `number-cell`, `date-cell` and `choice-cell`. The grid has column headers, row headers and typed cells, and it follows the ARIA grid pattern. The arrow keys, Home and End move the focus. Enter or a typed character opens the editor of a cell, Enter saves and Escape cancels. The grid refuses a value of the wrong type and shows the reason as text. Each saved change is one action with the row key, the column key and the value. The cell shows `Pending` until the receipt comes back, and `Not done` if the API refuses the change. The application binds the tool, its arguments, and the key, the label and the type of each row and column that a person can edit. A fill cannot make a cell editable or give a bound key a different label. New data from the application keeps the focus on the same cell. The kit computes no formula. A grid of 50 rows and 12 columns scrolls inside its own area with fixed headers. `mu-thread` shows a data grid part. `examples/tables/budget.html` shows a synthetic budget with a total row that the page computes. [src/components/data-grid.md](src/components/data-grid.md) gives the rules.
- The upload control `mu-upload` (#74), with the contract `upload`. A person picks or drops files. Page code binds the tool, the accepted types, the size limit and the file count, and a fill cannot set them. The control refuses a file of a wrong type, a file over the size limit and a file over the count before a request, and shows the reason as text. It never reads the content of a file and shows no preview. It sends a `mu-upload` event for each file, the application sends the file, and `Done` shows only after the receipt. The thread accepts upload parts. `examples/forms/upload.html` attaches synthetic PDF receipts to a ticket with the fixture API `tools/upload_server.py`, which keeps the files in memory only.
- The rich text component `mu-rich-text` (#75), with the contracts `rich-text`, `rich-paragraph`, `rich-heading`, `rich-list`, `rich-code`, `rich-quote`, `rich-span` and `rich-link`. A fill is a tree of typed nodes, never HTML and never Markdown. The element makes each element from a fixed list and writes each text into a text node. It refuses an unknown node type and an undeclared attribute. A link is a button with no address attribute. Page code sets the link schemes with `MuRichText.linkSchemes`. The default is `https:` only. The target shows as text on hover and on focus, and it opens only after a press and a cancelable `mu-open` event. Page code sets the first heading level with `MuRichText.headingLevel`, and a fill cannot skip a heading level. `mu-thread` shows a rich text part. Decision 0007 gives the reasons and the mapping from a Markdown subset. `examples/thread/rich-text.html` shows an agent message with a heading, a list of three steps and one link. [src/components/rich-text.md](src/components/rich-text.md) gives the rules.
- The diff component `mu-diff` (#30), with the contracts `diff`, `diff-part` and `diff-change`. A diff shows the changes between two versions of a text or a list of fields, in up to 20 parts of 200 changes. Each change shows its kind as text: `Added`, `Removed`, `Changed` or `Unchanged`. The element refuses a change whose values do not agree with its kind. Each part is a `details` element that a person opens and closes with a mouse or a keyboard. A diff of more than 20 changes starts with each part closed. `mu-thread` shows a diff part. `examples/evidence/diff.html` shows a diff of two synthetic versions. [catalog/README.md](catalog/README.md) gives the rules.
- Decision 0006 on axe-core (#39). The proposed choice rejects axe-core, so the kit keeps zero development dependencies. The record maps each axe-core risk that applies to the markup of the kit to a project rule. The browser check gets generic rules for each check page and each example: each control has a name, each id is unique, each id reference finds its target, and each role, ARIA value and `tabindex` is valid. `tests/browser/rules.html` has one defect of each kind, and the check fails if the rules miss one.
- The status component `mu-status` (#32) shows pending, passed, failed or unknown with short text, a fixed label and a border style. It refuses an undeclared state. `examples/cards/status.html` shows each state with synthetic data.
- The image component `mu-image` (#76) has page-set origins, a text alternative, a fixed box for loading and failure, and a full-size native dialog. The thread accepts image parts. `examples/media/image.html` shows a synthetic plan in a message and a card.
- The chart component `mu-chart` (#77) draws SVG bar, line and stacked bar charts with keyboard point controls and a table view. `examples/media/chart.html` shows synthetic data for each type.
- Typed form edits (#9). A field with `typed: true` asks for the edit type after a person changes its value: judgment, correction or override. The binding of the form gives the typed names and the person who edits, with `typed` and `editor`. The form refuses a fill whose typed flags do not agree with the binding. A changed typed field with no type sends no action, and the field shows `Choose an edit type.` The request gets an `edits` list. Each edit has the field, the type, the old value, the new value, the actor and the time. [catalog/README.md](catalog/README.md#typed-edits) gives the rules.
- Input types for a form (#34): `long-text-field`, `number-field`, `date-field` and `choice-field`, with the elements `mu-long-text-field`, `mu-number-field`, `mu-date-field` and `mu-choice-field`. A number field sends a number, and a number field and a date field accept an optional range. A choice field is a radio group of 1 to 20 choices. A form refuses a fill whose field data do not agree, for example a value outside the range. A value that a person types and that the field does not accept sends no action, and the field shows the reason as text. A typed edit works with each input type. A component field in a contract can now name 2 to 12 components with `names`. This changes `catalog/schema/contract.schema.json`. `examples/forms/inputs.html` shows each input type. [catalog/README.md](catalog/README.md#input-types) gives the rules.
- The form card `mu-form-card` (#72), with the contracts `form-card`, `form-section` and `form-line`. It shows a long form in sections as labels and values, with an optional line number. A person opens the editor of one field, then saves or cancels. A changed field shows `Changed` until the receipt. A read-only field has no editor, and the application gives new computed values with `card.computed(values)`. The card sends only the changed fields as one action, with typed edits. A card has up to 10 sections of 40 lines. `examples/forms/membership.html` shows a membership form of 25 fields in a thread. [catalog/README.md](catalog/README.md#form-card) gives the rules.
- The offline data source interface (#26). An application module, the source, gives records with `get(key)` and `list(filter)`. `read(source, request, options)` in `src/offline/source.js` checks the request and the result, and gives a frozen result with the state `ready`, `stale`, `empty` or `error`. A failed source, a source that does not answer and a result that is not valid show an error and no records. `mu-source-status` shows the state as text. `examples/cards/offline.html` shows each state, offline and online. [docs/contracts/data-source.md](docs/contracts/data-source.md) gives the rules.
- A deterministic check compares explicit narration claims with card values and reports each difference by field name. Decision 0005, tests and a synthetic example define its scope (#40).
- The table component `mu-table` (#31) shows text headers, rows and optional row status text, with keyboard sorting and an empty state. `examples/tables/table.html` shows synthetic rows.

## 0.2.1, 2026-11-14

- Four guides in `docs/guides/` (#63): contracts, page assembly, theming and coding agents. Each code block of a guide is an exact part of a checked file in `examples/guides/` or `catalog/`. The theming guide shows a second theme, `forest`. `tests/test_guides.py` and `tests/browser/guides.mjs` check the guides, and `tools/browser_check.mjs` runs the browser check in the four media modes. The README and `src/README.md` link the guides.
- The thread example server `tools/thread_server.py` handles a busy port (#64). If the default port is in use, it takes a free port and prints its URL. If a port that the user gives with `--port` is in use, it prints one line and exits with code 1. The quickstart gives the advice for a busy port.
- Three complete example apps in `examples/apps/` (#67): a support desk, a change review and a field inspection. They use one fixture API, `tools/apps_server.py`, with the Python standard library only. It binds to `127.0.0.1` and takes a free port if port 8770 is in use. `tests/test_apps_server.py` and `tests/browser/apps.mjs` check the API and the main flow of each app. The README lists each app in the quickstart.
- The README leads with UIs that a coding agent or a model builds from declared components (#65). It has a section for coding agents. One image sequence of `examples/thread/thread.html` replaces the screenshot gallery. `make screenshots` makes the four frames in the light theme and the dark theme from the example and its synthetic data. The gallery fixture `tests/browser/gallery.html` is removed.

## 0.2.0, 2026-11-13

- The registration of an application contract and element (#27). `register(contract, element)` checks the contract with the validator and the schema of the catalog, and it defines the element as `mu-app-<name>`. The frozen `CATALOG` does not change. `CONTRACTS` in `src/render/registry.js` gives the catalog contracts and the registered contracts to the elements, the envelope reader and the thread. The call refuses a catalog name, a name that is already registered, an invalid contract and an element that does not extend `MuElement`. `examples/cards/register.html` shows a registered domain component. [catalog/README.md](catalog/README.md) gives the limits.
- The approval example (#8). `examples/cards/approval.html` lists the open decisions as cards with their evidence. An approve or reject action goes to the fixture API `tools/approval_server.py`, which uses the Python standard library only. The button shows pending, and it shows done only after the receipt. The API refuses a second action on one decision, and the page shows the refusal as an error. `tests/browser/approval.mjs` checks the list, one approve with a receipt and one refusal.
- Decision 0002 on agent UI protocols (#51) and decision 0003 on shadow DOM (#50).
- Constitution versions 3 and 4 (#45, #48). Mugham is a UI toolkit for agentic applications. The kit has no runtime dependency, and the README screenshots are an exception to the rule against generated binaries.
- The workbench shell and the panels are out of scope (#41). The README no longer lists related projects (#43). The README and the status agree with the 0.1.0 state (#42).
- The gate pin moves to `mohanraj00/.github` at `b5d2b63` (#24).

- The source excerpt component `mu-excerpt` (#29). It shows a passage as text, with the span in a mark element. The mark has an underline and a strong weight, and the span shows again as text, so the mark does not depend on color. The span positions count code points. The element refuses a span that is empty or outside the passage. The required citation slot gives the source and the locator, so the locator rule of the slot applies. `mu-thread` shows an excerpt part. `examples/evidence/excerpt.html` shows an excerpt of a synthetic document.
- The citation component `mu-citation` (#28). It shows the source name, the locator as text, an optional quote and an `Open source` button. The source and the locator come from the citation slot, so the locator rule of the slot applies. A citation with no slot shows the `empty` state. A missing locator or a locator that is not a safe `https:` address gives a refusal with a clear reason. `mu-thread` shows a citation part. `examples/evidence/citation.html` shows a citation in a message. A base element can now give a refusal reason for a person with `refusal(errors)`. The `mu-refused` event still gives all errors.
- Contract format 2 gets the authorship slot and the citation slot (#33). A contract declares each slot, and each slot can be required. A fill gives the slots in its `slots` key. The validator refuses a fill that leaves a required slot empty. The kit shows each filled slot as text. A locator is an `https:` address, and it opens only after a person clicks `Open source`. Only the outer fill has slots. Format 2 is not released, so the format number stays `2`.
- The flag `ai_content` now has an effect. A contract with `ai_content` set to `true` must declare a required authorship slot. Thus the fills of `card`, `card-grid`, `editable-form` and `fact` must name the actor that wrote the content. A fill of these components with no `slots.authorship` is refused.
- Each element gets an `actor` property (#33). The application or the thread sets it to the trusted actor of the content. An element refuses a fill whose authorship slot has no bound actor, or names a different actor. The `type`, the `id` and an optional `name` must agree with the bound actor. Thus a model cannot show its content as the content of a person. `mu-thread` sets the actor of each component part to the actor of the envelope. The fills of `examples/thread/thread-events.json` and of the thread checks now name their author.
- The example page `examples/evidence/provenance.html` shows a card with the two slots, and a card that the kit refuses because its authorship slot is empty.
- `mu-thread` updates the page one time for each frame, not one time for each task. An event that changes no message, no run and no error gives no update. The `push` function of the envelope reader gives `false` for such an event. Thus a stream of unknown events cannot use the CPU of the page (#57).
- The thread `mu-thread` for people and agents. It reads AG-UI 1.0 events through `src/envelope/`, from any async source. Each message shows its actor and the actor type. A message with no end marker shows as partial. A run error shows as an error, and a refused part shows a refusal notice. An action goes to the application and shows `Done` only after its receipt. A polite live region announces new messages, and the focus does not move. `src/thread/README.md` is its contract.
- `examples/thread/thread.html` and `tools/thread_server.py`: two people and two agents in one thread, over server-sent events from a Python standard library server. The server gives the receipt of each action.
- The message envelope, version 1, in `docs/contracts/`. It maps AG-UI 1.0, as decision 0002 says. `src/envelope/envelope.js` reads an envelope and an AG-UI stream. Each message has an actor, typed parts and an honest state. `tests/vectors/envelope/` has the conformance cases. `generate.py` in that folder writes them, and `tests/test_envelope_vectors.py` compares them with its output.
- Contract format 2. Format 1 had an `actions` block in a contract and an `actions` list in a fill, but they had no effect. Format 2 removes them. Each contract now has `"format": 2`. A fill with an `actions` key is refused. The application binds each action in code, as `catalog/README.md` says.
- An action binding can have a confirm step: `confirm: { message, label }`. `mu-action-button` and `mu-editable-form` then show the step, with the new state `confirm`. They send the action only after a person confirms. Cancel and Escape send no action.
- A receipt can carry a `reference`, for example a record id. The element shows it as text, with 80 characters maximum. A receipt with a longer reference is refused.
- `catalog/README.md` is the one description of the action model. `catalog/schema/README.md` and decision 0002 refer to it.
- A release workflow attaches `mugham.tar` and a SHA-256 file to a GitHub release. It publishes no package. [Decision 0004](docs/decisions/0004-package.md) gives the package choice.
- The README has a quickstart, the minimum browser versions and a stability statement.
- The README is for people. It lists each catalog component, and it shows the highlights of the kit in screenshots for the light theme and the dark theme. Agents and LLMs go to the constitution and `AGENTS.md`.
- `make screenshots` writes the README screenshots to `docs/screenshots/` from a fixture page with synthetic data.
- Fix: an action button with no description showed the text `null`.
